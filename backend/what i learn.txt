Records can be a good choice when you want value-based equality or immutable data, especially for response DTOs. But request DTOs are commonly mutable for JSON binding and validation, and switching to records doesn’t make the API more correct or faster by itself.


AppDbContextFactory is responsible for creating an instance of AppDbContext, usually for Entity Framework Core design-time operations.EF Core how to create that DbContext, even without running your application and understand entity and database configuration.
EF Core can create a DbContext in several ways:
1. From your application’s Dependency Injection (DI) — it uses the configuration in Program.cs.
2. Through AppDbContextFactory — it uses the factory's CreateDbContext() method.
Why use a factory, then?
Suppose your Program.cs contains:

builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(connectionString));


EF Core can often use this configuration to create your context for migrations. No factory needed.

But if EF Core cannot construct your context reliably at design time, a factory provides an explicit way to create it.

Repository pattern: BaseRepo<T> can own shared CRUD operations, while entity-specific repositories add reusable queries that match the domain (for example, finding schedule conflicts or calculating an invoice balance). Keep business workflows out of repositories unless they are specifically data-access concerns.

Database integrity must be enforced by the database when it needs to hold for every writer, not only checked in application code. A repository conflict check is useful feedback, but two requests can both pass it before either saves. A database constraint or trigger is the last line of defense against that race.

Time intervals overlap when start1 < end2 AND start2 < end1. Using strict comparisons means back-to-back appointments are allowed. Cancelled appointments should not block a time slot, so the status rule belongs in both the conflict query and the database trigger.

SQLite stores EF Core decimal values as TEXT by default. Numeric CHECK constraints should CAST the value to NUMERIC before comparing it, so zero or negative amounts cannot pass because of SQLite's type comparison rules.

Invoice balances need to account for partial payments: sum only completed payments, subtract that total from the invoice amount, and avoid returning a negative outstanding balance. A missing invoice is different from a zero balance.

EF Core migrations version database schema changes. Model configuration describes the intended schema, the migration applies the change to existing databases, and the model snapshot lets EF detect future differences. Database-specific objects such as SQLite triggers may need explicit SQL in a migration.

API contracts should validate at the edge. Data annotations like [Required], [EmailAddress], [StringLength], and [Range] catch bad requests early, but domain rules still belong in services and database constraints. A strong API design validates both the request shape and the business meaning.

JWT authentication works best when the token contains only the minimum claims needed for authorization, and the signing key is long enough and kept secret. In practice, the server should validate issuer, audience, expiration, and signature on every request, and the client should only receive the token after successful login.

Middleware is useful for cross-cutting concerns like exception handling, rate limiting, and request logging. Handling exceptions centrally keeps controllers cleaner and makes the API responses consistent, especially when you want to hide internal details while still returning actionable client errors.

Rate limiting protects public endpoints from brute-force or abuse, but it is only effective when the key is based on a meaningful client identifier, such as IP address, and the limit is tuned to realistic usage. The API should return a clear Retry-After header so clients know when to retry.

Names and routes should be predictable. For example, controller actions like /api/auth/login and /api/doctors/available communicate purpose clearly, and consistent route naming improves both client code and maintainability.

A well-structured service layer keeps controllers thin. Controllers should translate HTTP concerns into domain operations, while services handle business rules like slot generation, appointment booking, duplicate detection, and patient anonymization.

Testing with WebApplicationFactory is valuable for integration testing ASP.NET Core apps because it boots the real application pipeline in a test host. This lets us verify routing, model binding, authorization, serialization, and app-level behavior without mocking everything away.

Database constraints and transaction boundaries matter. Even if the application checks for conflicts before creating a record, a second request may race in between. Transactions and database-level validation help avoid inconsistent states.

Documenting what you learn matters because patterns become easier to reuse later. Good learning notes capture why a design exists, not just what it is: e.g., why records are useful, why EF Core factories exist, why constraints matter, and how JWT and validation protect the API.

The best API code usually balances three things: correctness, security, and simplicity. Simple code is easy to maintain, correct code avoids bad data, and secure code limits exposure to common attack patterns such as injection, overexposure of secrets, and invalid authorization.
